## Implemented

`AuthenticatedGiteaReadCompletionObserver` is a **concrete, read-only**
`TrustedAuthorityOnlyCompletionObserver` implementation. It can be
installed by a trusted Gateway owner in place of R293's test callback.

A required **owner-only prepublished evidence file** is looked up by the
hash of its exact `session_id + request_id`. The reader rejects a missing
file, wrong file type, symlink, hard-link, shared directory or permissions,
extra/absent fields, unsigned/invalid HMAC, wrong Task, epoch, agent DID,
Child ID, root, authority digest, prepared request fingerprint, unconfirmed
Rust/OPA/provider success, or old/future result. It requires a separate
32+-byte trusted HMAC key (not the Engineer signing key).

It uses the existing authenticated `GiteaClient` with an independently
provisioned read-only Gitea token to read the feature branch HEAD, fetch
the exact file at the receipt's pinned SHA, and recheck HEAD. Branch
movement, blob SHA mismatch, byte size mismatch, or SHA-256 content
mismatch denies. Only the evidence hash and exact immutable Task pins
reach the Gateway completion observer; private source bytes do not.

The gateway's R293 durable one-flight and one-completion journals and
dependency attestation remain in force. Its provider execution remains
disabled. The R294 reader **never generates receipts** or grants rights.

## Offline verification

`trusted-authority-only-gitea-evidence.test.ts` exercises the concrete
GiteaClient parse/HTTP authorization and MAC/file/HEAD verification
against deterministic simulated Gitea responses, plus negative tests
for foreign Child/Task/epoch, wrong key, forged status, altered contents,
moved HEAD, missing and symlinked receipts.

## Remaining blocker before production claims

The R292 native Rust/EVM+OPA verification was real, but its Gateway
provider call count was **zero**. There is currently **no trusted writer**
for the new authority-only provider-success evidence record: current
authority-only Gateway execution intentionally terminates before Gitea.
An arbitrary file MAC generated by another owner process is *not* proof
that an authorized provider effect actually occurred.

**Next:** bind receipt publication exclusively to real Gateway execution
after verified VP, OPA and successful authenticated Gitea/Runner result;
establish trusted host secret ownership and result append-only durability.
Then add per-effect sequential journal accounting for multiple tools per
Task, and prove the complete scripted provider path before lifting the
terminal denial. Until then, do not use mocked test receipts to unblock
real Task dependencies.

No paid models, no changes to `main`, no old signed-DAG fallback.
